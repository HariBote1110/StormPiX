# StormPiX — やりたいことの整理

画像を Stormworks の Lua 描画コードへ変換するツールを、既存2実装より効率的かつ現代的に作り直す。

## 1. 前提（確定した制約）

- Lua スクリプト1個あたり **8192文字** が上限。これが唯一の希少資源。
- モニターは 1ブロック = 32x32 px。1x1=32x32、3x3=96x96、5x3=160x96、9x5=288x160 など。
- 描画は `onDraw()` 内。`screen.setColor(r,g,b,a)` / `drawRectF` / `drawRect` / `drawLine` / `drawText` / `drawCircleF` など。
- 色は 0-255。ゲーム側でガンマ／モニター発色の癖があるため、忠実プレビューには補正が必要。

## 2. 既存2ツールの評価

| | Stormworks-PixelTracer (doma-itachi) | storm-kamishibai (nona-takahara) |
|---|---|---|
| スタック | 素の HTML/JS/CSS | TypeScript + Vue + Vite |
| 強み | レイヤー、プレビュー、自動トレース＋自動色付け、ミニファイ、ガンマ補正 | 数値入力による複数コマ切り替え |
| 状態 | MIT | MIT / **メンテナンスモード（Pages 停止予定）** |

単一画像の最適化は前者、複数コマは後者に分かれており、両方を満たす現代的な実装が存在しない。

## 3. 本ツールの核心

このツールの本質は「画像 → Lua 変換」ではなく、

> **8192文字の予算内で、元画像との視覚的差分を最小化する描画命令列を探す離散最適化**

である。文字数を明示的な目的関数として扱うことが、既存ツールとの決定的な差になる。

### コスト関数の非自明さ
`drawRectF(x,y,w,h)` のコストは引数の**桁数**で決まる。座標が小さいほど、値が使い回せるほど安い。
面積ベースの貪欲な矩形結合は、文字数ベースでは最適から離れる。

### 最適化の3レイヤー

1. **矩形被覆** — 同色領域を、文字数をコストとした最小被覆問題として解く（走査ベースの貪欲結合ではない）。
2. **色の量子化と描画順序** — パレット削減（メディアンカット / k-means＋CIEDE2000）とディザリングを文字数予算とのトレードオフで選択。`setColor` 呼び出し回数は色数と描画順に依存するため、色ごとにまとめる順序最適化が効く。
3. **コード生成戦略の自動選択** — 命令列の直書きと「データ＋デコーダ」（座標テーブル、`string.byte` による RLE 展開、ループ、ローカルエイリアス）には、画像の複雑さに応じた損益分岐点がある。両方生成して安い方を採る。

## 4. スコープ

### 含める
- 静的 SPA（ブラウザ完結、インストール不要）。重い探索は Web Worker、必要なら WASM。
- 文字数を目的関数とした本格的な探索最適化。
- **複数フレーム / アニメーション**: フレーム間差分のみ描画、共通パレット、tick ベース再生。
- 変換コアは UI から独立させた純粋関数として実装し、PSNR/SSIM による回帰テストとベンチマークを回せる形にする。

### 今回は優先しない（将来の拡張候補）
- レイヤー / 部分更新
- テキスト・ビットマップフォントの活用（`drawText` は文字数効率が極めて良いので、拡張時の第一候補）
- モニター構成プリセット / 実寸忠実プレビュー（最小限のプレビューは当然入れる）

## 5. 品質の測り方

ベースラインとして既存2ツールの出力を用意し、同一画像・同一文字数予算で比較する:
- 予算内に収まった上での SSIM / PSNR
- 同一視覚品質を達成するのに要した文字数
- 変換所要時間

これを最初に自動化しておかないと「効率的になった」と主張できない。
