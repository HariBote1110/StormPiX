# 決定的な探索仕事量（Phase 9）

## 目的

`convert()` と `convertFrames()` の探索終了条件を壁時計からカウント済みの仕事量へ変更した。以前は `timeBudgetMs` の期限を候補探索の各段階で直接確認していたため、同じ入力・seedでもCPU負荷によって候補数が変わり、Lua、品質、paddingの保証が崩れていた。

## 実装判断

- 候補評価、初期候補、低予算リファインメントの各試行を1仕事として数える。
- 通常の `convert()` は既定仕事量60、`convertFrames()` は40とする。高予算の単一画像は12候補までに抑え、既存の品質・文字数を保ったままベンチの探索時間を約1秒へ収めた。
- `timeBudgetMs` は公開APIから削除せず、探索の強さを決める決定的なスケーリング入力とした。壁時計の安全弁は設けない。仕事量は次式で決定する。

  `floor(defaultWorkBudget * sqrt(clamp(timeBudgetMs, 1, 5000) / 5000))`

  ただし1以上を保証し、通常の単一画像の高予算経路には上限12を適用する。したがって、呼び出し側が小さい時間予算を指定した場合は、それに比例して小さい仕事量になり、同一値ならマシン速度によらず同じ探索結果になる。
- `ConvertStats.timeBudgetTruncated === true` は、カウント済み仕事量を使い切ったことを示す。仕事量制御を通らない経路、または仕事量を使い切らずに探索を終えた経路では `false` になる。既存の `ConvertStats` 互換性のため追加フィールドは任意とした。
- `elapsedMs` は計測値として残すが、結果の選択には使わない。

## 検証

決定性テストは `performance.now()` を固定したアイドル時計と、同じ仕事量中に時間だけ進む負荷時計でLuaを比較する。30フレーム・96×32・256色の合成アニメーションでは、旧deadline実装でアイドル側と負荷側のLuaが異なって失敗し、deadlineを除いた後は両者が一致することを確認する。

Lua 5.5の実行器、既存ベンチ、実アセット回帰は変更せず、仕事量化後も既存の文字数・SSIMを維持した。Lua実行器は別途Lua 5.3 WASMへ差し替え可能な小さい境界を保つ。

## 未解決事項

極端に小さい `timeBudgetMs` は少ない仕事量へ決定的に写像されるため、品質が下がることがある。仕事量の既定値や高予算上限の再調整は、最適化アルゴリズムの変更を伴わない将来の計測課題とする。
